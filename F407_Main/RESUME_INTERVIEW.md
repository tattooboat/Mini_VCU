# Mini VCU 项目：简历与面试材料

项目名称建议：**STM32F103/F407 分布式电机控制与 LVGL 车载仪表盘**

## 一、一句话项目介绍

基于 STM32F103 和 STM32F407 搭建 CAN 双节点电机控制系统，在 F407 上完成 `0x301/0x302` 应用层协议、编码器速度 PI、TB6612 驱动、故障保护，并整合 ILI9341、XPT2046 和 LVGL 实现本地触摸控制与真实状态仪表盘。

## 二、简历项目描述

### 推荐版本

**STM32 分布式电机控制与 LVGL 仪表盘｜个人项目**

- 基于 STM32F103/F407、FreeRTOS 和经典 CAN 2.0A 搭建双节点系统，定义 `0x301` 电机控制帧与 `0x302` 反馈帧，实现 250 kbit/s 通信、序号回传和多级帧校验。
- 在 F407 上使用 TIM8 正交编码器、速度 PI、积分/PWM 限幅和 TB6612FNG 实现转速闭环；加入 500 ms CAN 超时停机、非法帧故障位和软件急停锁存。
- 将 ILI9341、XPT2046、LVGL 接入 FreeRTOS，完成主页/控制页、页面切换、触摸启停与调速，并把目标转速、实测转速、PWM、CAN 在线状态和故障实时显示到屏幕。
- 设计“E-STOP > STOP > 本地触摸 > CAN”的控制仲裁，确保 LVGL 回调不直接操作 PWM；修复 LVGL 渲染栈溢出、静态演示值、浮点显示乱码和按钮命中困难等问题。

### 更偏嵌入式软件岗位

- 整合 STM32 HAL、FreeRTOS、CAN 中断、定时器编码器、PWM、I2C、ADC 与 LVGL 显示框架，完成多任务和中断数据交互。
- 通过 `HAL_CAN_RxFifo0MsgPendingCallback()` 接收 CAN 帧，在中断内完成帧头、命令、DLC 和速度范围校验，在任务上下文执行闭环和 UI 刷新。
- 对故障标志读改写使用 PRIMASK 临界区，避免 CAN 中断与控制任务并发更新时丢失故障位。

### 更偏 GUI/显示岗位

- 在 STM32F407 的 320×240 RGB565 屏上移植 LVGL，配置 10 行局部渲染缓冲和 33 ms 刷新周期，实现主页、控制页与触摸事件。
- 完成 XPT2046 原始坐标到 LVGL 屏幕坐标的旋转映射，将页面固定、三行两列大按钮和实时状态刷新结合，改善触摸命中率与显示可读性。

## 三、一分钟项目介绍

> 这个项目是一个两块 STM32 组成的车载电机控制原型。F103 作为发送端，通过 CAN 每 50 ms 发送 `0x301` 控制帧，并支持构造错误 DLC、帧头、命令和速度等异常帧；F407 作为主控，在 CAN 接收中断中完成校验，再由 FreeRTOS 的高优先级电机任务把 `-1000~1000` 的指令映射成目标 RPM，读取 TIM8 编码器实际转速，用 PI 输出 TIM3 PWM 驱动 TB6612。
>
> 后续我在 F407 上加入了 ILI9341、XPT2046 和 LVGL，做主页和控制页。控制页可以触摸启动、停止、每次 10 RPM 调速、急停和复位，并显示目标转速、编码器实测转速、PWM、CAN 状态和故障。控制权不是直接写在 LVGL 回调里，而是通过应用层目标仲裁：急停锁存优先级最高，其次是 STOP 锁存、本地触摸，最后才是 CAN。这样能保证触摸控件只发请求，电机输出始终由统一任务管理。
>
> 当前 F407 固件构建为 0 错误、0 警告，镜像约 291 KB Flash、116 KB RAM。项目还有明确的测试边界：显示、触摸和 LVGL 页面已有上板记录，CAN 和 PI 有部分闭环测试，但编码器绝对 RPM、实时性、触摸精度和硬件急停仍需继续验证。

## 四、五分钟技术讲解结构

### 1. 项目背景

目标不是只让电机转起来，而是演示一条完整链路：

```text
遥控 CAN 指令 / 本地触摸指令
        → 目标源仲裁
        → 编码器转速闭环
        → PWM 驱动
        → 真实状态回显
```

同时通过 F103 发送端模拟远端控制和非法帧，验证 F407 的接收校验和故障处理。

### 2. 系统分层

- 输入层：CAN、XPT2046、ADC、AHT20。
- 应用层：目标源仲裁、CAN 协议、故障位、本地控制。
- 控制层：目标 RPM、编码器反馈 PI、积分/输出限幅。
- 驱动层：CAN1、TIM3 PWM、TIM8 编码器、GPIO 模拟 SPI、I2C。
- 显示层：ILI9341、LVGL、主页/控制页。
- OS 层：FreeRTOS/CMSIS-RTOS2，1000 Hz tick，按周期和优先级调度。

### 3. 电机闭环

```text
can_speed(-1000~1000)
    → target_rpm = can_speed / 1000 × 169
    → error = target_rpm - actual_rpm
    → integral 限幅 ±400
    → output = Kp × error + Ki × integral
    → PWM 限幅 ±1000
    → TB6612
```

当前实际为 PI，不是 PID。目标变化超过 5 RPM 时会清积分；目标为 0 时清积分并停止 PWM。

### 4. CAN 安全

- `0x301` 必须是标准数据帧、DLC=8、帧头 `0xA5`、命令 SET/STOP、速度范围合法。
- 非法帧不覆盖上一条合法目标，也不刷新接收时间。
- 超过 500 ms 没有合法帧则目标归零，置 `FAULT_CAN_TIMEOUT`。
- `0x302` 回传状态、目标值、命令、序号和故障码。

### 5. LVGL 整合

- 320×240 RGB565，LVGL 内存池 80 KB，单缓冲 10 行。
- `lv_timer_handler()` 放在低优先级 `lcdTask` 中，每 5 ms 运行一次。
- 触摸由 XPT2046 周期采样并注册为 LVGL pointer 输入。
- 控制页每 200 ms 刷新目标、实测、PWM、运行状态和 CAN 状态。
- LVGL 回调不直接调用 PWM，只修改 `App_MotorControl` 中的请求。

### 6. 关键问题

- 2 KB UI 栈在 LVGL 渲染时溢出，提高到 8 KB。
- 静态演示值无法反映真实控制状态，改为控制任务发布的实测值。
- 设备端浮点格式显示异常，速度改用整数格式化。
- 触摸页面可滚动且按钮过小，最终禁用滚动并改为三行两列大按钮。
- 本地控制和 CAN 会争夺控制权，最终定义锁存优先级和 RESET 回归流程。

## 五、适合展开讲的 STAR 案例

### 案例 1：LVGL 页面栈溢出

**S**：接入 LVGL 后，页面创建或渲染时任务不稳定。  
**T**：在保持其他任务和驱动可运行的前提下定位问题。  
**A**：检查任务栈、LVGL 内存池、刷新路径和回调执行上下文，发现原 UI 任务只有 2 KB 栈，而 LVGL 静态调用图的最大栈使用约 1.3 KB，叠加 HAL 调用和局部变量后余量不足；将 UI 任务栈提高到 8 KB。  
**R**：页面创建和渲染恢复稳定，并通过链接器调用图确认 LVGL 最深层调用路径。

展示重点：不是简单“加大栈”，而是从调用图、内存配置和执行上下文定位。

### 案例 2：静态仪表盘改为真实数据

**S**：早期主页显示 `120 km/h`、`PWM 0%` 等演示值，无法证明控制链真实工作。  
**T**：让 UI 显示目标转速、编码器实测转速、PWM 和故障状态。  
**A**：由 `Motor_CAN` 任务统一发布 `g_ui_target_rpm / g_ui_actual_rpm / g_ui_pwm`，LVGL 任务每 200 ms 快照并刷新控件；实际值来自编码器和 PI 输出，而不是 UI 本地计算。  
**R**：主页和控制页能够区分目标值与实际值，并同时支持 CAN 和本地触摸控制。

### 案例 3：本地控制与 CAN 争抢电机

**S**：F103 持续发送 `0x301` 时，本地 STOP 可能被下一帧 SET 重新覆盖。  
**T**：建立明确的控制权和安全状态。  
**A**：定义 `E-STOP > STOP latch > local active > CAN` 的优先级；本地 STOP 和 E-STOP 都进入锁存，只有显式 RESET 才释放。  
**R**：停止状态不会被残留 CAN 帧误启动，控制权切换具有明确入口。

### 案例 4：设备端浮点显示乱码

**S**：主页速度曾出现 `frmp` 等异常字符。  
**T**：修复显示并保留转速信息。  
**A**：检查 LVGL 格式化路径和设备端 printf 支持，将浮点速度改为四舍五入后的整数，再用 `%d` 输出。  
**R**：乱码消失，速度显示清晰，避免继续依赖设备端浮点 printf。

## 六、模块与技术点速查

### RTOS

- tick：1000 Hz。
- 电机任务：High，50 ms。
- UI 任务：Low，8 KB 栈，5 ms 循环，LVGL 刷新周期约 33 ms。
- 传感器任务：Normal，500 ms。
- 所有 LVGL API 都在 UI 任务上下文调用，没有在 CAN 中断中绘图。

### CAN

- 250 kbit/s，标准数据帧。
- `0x301` 控制，`0x302` 反馈。
- 帧校验顺序：ID → DLC → 帧头 → 命令 → 速度范围。
- 500 ms 无合法帧超时。
- 故障位可叠加，测试时按位判断，不要只比较精确值。

### LVGL/显示

- 320×240，RGB565。
- LVGL 内存 80 KB。
- 单缓冲，10 行，6400 B。
- 显示使用 GPIO 模拟 SPI，同步区域写屏。
- 触摸坐标固定标定：原始 Y → 屏幕 X，原始 X → 屏幕 Y。

### 电机/编码器

- TB6612：PWM `PB0`，AIN1 `PB12`，AIN2 `PB13`，STBY `PB14`。
- 编码器：TIM8，`PC6/PC7`。
- 输出轴 RPM = 计数差 × 60 /（44 × 采样周期 × 35.5）。
- 当前映射上限 169 RPM，UI 本地限幅 ±150 RPM。

## 七、面试问答

### Q1：为什么用两块 MCU？

> 一块 F407 也能完成这个规模的功能。这个项目使用 F103 + F407 主要是为了形成真实的分布式 CAN 链路，并让 F103 单独承担指令发送和故障注入。发送端断电或发送非法帧时，可以独立验证 F407 的超时、校验和安全停机，不需要把测试逻辑塞进电机控制节点。

### Q2：为什么选择 LVGL，而不是继续手写绘图？

> 早期手写 LCD 驱动已经能画矩形、字符和静态主页，但页面切换、按钮事件、控件布局和样式维护会越来越复杂。LVGL 提供对象树、事件、布局和局部刷新，更适合做多页面交互。代价是栈、Flash/RAM 和刷新带宽都要重新评估。

### Q3：为什么没有启用 LVGL 的 FreeRTOS OS 模式？

> 当前所有 LVGL 调用都集中在唯一的 `lcdTask` 中，数据刷新也只在同一任务中执行，因此 `LV_OS_NONE` 可以避免引入额外锁和线程。代价是不能从其他任务或中断直接调用 LVGL。如果以后增加多个生产者，应启用 LVGL OS 支持或通过队列把更新请求集中到 UI 任务。

### Q4：LVGL 内存和任务栈怎么评估？

> 当前配置是 80 KB LVGL 内存池、8 KB UI 任务栈、单缓冲 10 行 RGB565，即 320×10×2=6400 B。这个配置已在 F407 上编译和运行，但还没有正式记录 LVGL `mem_used`、任务栈高水位和长时间运行碎片，所以不能说已经完成最坏情况评估。

### Q5：触摸坐标怎么接入 LVGL？

> XPT2046 先读取原始 X/Y，再由 `App_Touch_Map()` 旋转映射到 320×240。映射后注册为 LVGL pointer 输入设备，LVGL 在输入周期调用回调读取按下状态和坐标。当前标定范围是硬编码的，更换屏幕或触摸控制器后必须重新校准。

### Q6：为什么 LVGL 回调不能直接写 PWM？

> 因为同一电机还有 CAN 目标源、超时保护和急停状态。如果控件直接写 PWM，会绕过控制权仲裁和积分限幅。当前回调只调用 `App_MotorControl_SetSpeed/Stop/EMStop`，电机任务在下一个 50 ms 周期决定最终目标并执行 PI。

### Q7：STOP、E-STOP、RESET 有什么区别？

> STOP 是普通停机锁存，阻止后续 CAN 帧重新启动；RESET 在普通停机时可以释放锁存，把控制权交还 CAN。E-STOP 是更高优先级的软件急停，立即清零目标、PWM 和方向输出，并锁存到显式 RESET。两者都不是硬件安全回路。

### Q8：为什么使用 PI 而不是 PID？

> 速度环的被控对象是带减速箱和惯性的电机，速度误差的微分容易放大编码器量化和噪声。当前使用 PI，配合积分限幅、PWM 限幅和目标突变时清积分。没有 D 项不等于不能控制，而是需要结合反馈质量和噪声实测决定。

### Q9：怎样保证 CAN 中断和任务的数据一致？

> `target_speed` 和 `last_rx_tick` 由单写者中断、单读者任务访问，并声明为 `volatile`；Cortex-M 上对齐的 16/32 位读写是原子的。故障位是读改写，使用保存/恢复 PRIMASK 的短临界区。更复杂的多字段更新会改成消息队列或双缓冲快照。

### Q10：收到非法 CAN 帧会立即停车吗？

> 不会。非法帧只置故障位，不更新合法目标和最后接收时间。如果后续没有合法帧，500 ms 超时后目标归零。这个行为需要和“坏帧立即停车”的产品需求区分；当前控制节点是原型。

### Q11：如何确认编码器转速准确？

> 当前按 11 脉冲、4 倍频和 35.5 减速比换算，参数仍是标定假设。正确方法是让电机运行已知输出轴转数，比较编码器累计值，或用外部转速表对比多个稳态点，并检查正反转符号。当前没有编码器断线故障位，这也是后续改进。

### Q12：显示刷新会不会影响电机控制？

> 电机任务优先级最高，LVGL 是低优先级任务；但 LCD 的同步 GPIO 模拟 SPI 会长时间占用 CPU，仍可能影响系统整体响应。当前没有量化 flush 时间和任务抖动。后续应把显示改到硬件 SPI/DMA、双缓冲，并用 GPIO 翻转测量控制周期。

### Q13：如果现场出现触摸不灵，怎么办？

> 依次检查供电和地、触摸片选、原始坐标范围、坐标轴方向、按钮命中尺寸、页面是否滚动、是否存在重复输入读取。当前已经通过禁用页面滚动、扩大按钮、修正坐标映射降低了误触。

### Q14：项目目前最大的不足是什么？

> 不是功能数量，而是验证深度。当前有编译、显示/触摸和部分闭环记录，但缺少统一的实时性、内存高水位、故障注入和长时运行报告。下一步会先补测量，再继续加功能。
